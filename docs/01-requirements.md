# 01. 要件定義書

そろばん（Soroban）— メルカリ転売 利益管理ツール

---

## 1. 何を解決するか

メロジョイ（Shopify）で仕入れた商品をメルカリで販売している。困っているのは以下。

| # | 課題 |
|---|---|
| 1 | いつ・何円で買った商品が、どの販売に対応するのか分からない |
| 2 | 販売手数料・送料を引いた**実際の利益**が見えない |
| 3 | 仕入先アカウントが2つあり、混ざる |
| 4 | 全部が転売ではない（私物の売却も混在）ため、税務上の切り分けができない |
| 5 | 売れ残りがいくら寝ているのか分からない |

**この製品の核心は「仕入と販売の紐付け」である。** ここが壊れると原価が出ず、全てが無意味になる。

---

## 2. 前提と制約

### 2.1 データ取得の制約

| 対象 | API | CSV |
|---|---|---|
| メルカリ（個人アカウント） | なし | **なし** |
| メロジョイ（Shopify・購入者側） | なし | なし |

メルカリの個人出品者向けに公開APIはなく、売上CSVのダウンロード機能もない
（CSV出力があるのはメルカリShopsのみ）。したがって画面からの取得か手入力しか選択肢がない。

### 2.2 規模

| 項目 | 値 |
|---|---|
| 月間取引数 | 20〜50件 |
| 1日あたり | 1〜2件 |
| 取り込み頻度 | 1日2〜3回で十分 |
| 仕入先アカウント | 2つ |

**この規模なら完全自動化に固執しなくてよい。**
「自動化の確実性」より「壊れても運用が止まらないこと」を優先する。

---

## 3. 構成

**単一のElectronアプリ。外部サービスなし。**

```
┌──────────────────────────────────┐
│  そろばん（Electron）             │
│                                  │
│  ┌────────────┐  ┌────────────┐  │
│  │ 収集        │  │ 画面        │  │
│  │ 埋め込み     │  │ Vue 3      │  │
│  │ ブラウザ     │  │            │  │
│  └─────┬──────┘  └─────┬──────┘  │
│        └────────┬───────┘         │
│                 ↓                 │
│        ┌─────────────────┐        │
│        │ SQLite（1ファイル）│        │
│        └─────────────────┘        │
└──────────────────────────────────┘
        Windows / macOS
```

| 項目 | 選択 |
|---|---|
| シェル | Electron |
| 画面 | Vue 3 + Vite |
| DB | SQLite（better-sqlite3）。userData配下に1ファイル |
| 収集 | 埋め込みブラウザ（persistパーティション） |

### 3.1 この構成の代償

| 失うもの | 対処 |
|---|---|
| 別端末から見られない | 割り切る。必要になったら同期を後付けする |
| DBが1ファイルなので壊れたら終わり | **バックアップとCSV書き出しを標準搭載する** |
| OSスケジューラがない | アプリ起動時に、前回から間隔が空いていれば取り込む |

### 3.2 ログイン方式

**認証情報をアプリに保存しない。**

初回のみ埋め込みブラウザが開くので手でログインする。Cookieを含むプロファイルを
`persist:mercari` パーティションに保存し、以後は再利用する。ログイン処理自体が存在しない。

2段階認証やSMS確認が挟まっても、手でログインするだけなので破綻しない。

## 4. 機能要件

優先度：**MUST**=Phase 1 / **SHOULD**=Phase 2

### 4.1 仕入

| ID | 要件 | 優先度 |
|---|---|---|
| P-01 | 仕入を登録できる。注文日・仕入先・注文番号 | MUST |
| P-02 | 1注文に複数明細。商品名・単価・数量 | MUST |
| P-03 | 仕入送料・割引を明細に**按分**して原価に含める | MUST |
| P-04 | 仕入先アカウントを区別する | MUST |
| P-05 | 明細の数量分だけ在庫アイテムを自動生成する | MUST |

**P-03の重要性**：送料1,000円の注文で5点買ったら1点あたり200円が原価に乗る。
無視すると利益が実態より大きく出る。金額按分・数量按分を選べること。

### 4.2 在庫

| ID | 要件 | 優先度 |
|---|---|---|
| I-01 | 在庫アイテム＝販売可能な1点を単位とする | MUST |
| I-02 | 各在庫は按分後原価（landed cost）を持つ | MUST |
| I-03 | 未販売在庫の点数と原価合計を表示する | MUST |
| I-04 | 滞留日数を表示し、長期のものを警告する | MUST |
| I-05 | 廃棄・自家消費を記録できる | MUST |

**I-04の重要性**：転売で最も効く指標。利益率が高くても半年寝ていれば資金効率は悪い。

### 4.3 販売

| ID | 要件 | 優先度 |
|---|---|---|
| S-01 | メルカリの売却済み取引を取り込む | MUST |
| S-02 | 手入力でも登録できる | MUST |
| S-03 | 発送方法を選択し、送料をマスタから自動計算する | MUST |
| S-04 | 販売手数料を料率から自動計算する（既定10%） | MUST |
| S-05 | **転売品か私物かを区別する** | MUST |
| S-06 | 1つの販売に複数の在庫を紐付けられる（まとめ売り） | MUST |
| S-07 | 梱包材費を計上できる | SHOULD |

**S-05の重要性**：私物の生活用動産の売却と転売所得は税務上の扱いが異なる。
混在したまま集計すると申告の根拠にならない。

**S-06の重要性**：メルカリではセット販売が頻繁に起きる。1販売＝1仕入と決め打つと破綻する。

### 4.4 紐付け

| ID | 要件 | 優先度 |
|---|---|---|
| M-01 | 販売に在庫を手動で紐付けられる | MUST |
| M-02 | 未紐付けの販売を一覧で表示する | MUST |
| M-03 | 商品名の類似度で候補を提示する | MUST |
| M-04 | 紐付け中に粗利が即座に見える | MUST |
| M-05 | 紐付けを解除・付け替えできる | MUST |

**完全自動で紐付けない。** 誤紐付けは原価を壊し、しかも気づきにくい。
候補提示までに留め、確定は人間が行う。**例外は Phase 2 の型番完全一致（M-06）だけ。**

### 4.5 利益計算

```
粗利 = 販売価格
     − 販売手数料（販売価格 × 料率）
     − 発送送料
     − 梱包材費
     − Σ(紐付けた在庫の按分後原価)
```

| ID | 要件 | 優先度 |
|---|---|---|
| R-01 | 販売ごとの粗利を算出する | MUST |
| R-02 | 月次の売上・原価・利益を集計する | MUST |
| R-03 | 転売分と私物分を分けて集計する | MUST |
| R-04 | CSVで書き出せる | MUST |
| R-05 | 振込手数料を期間費用として計上する。**月1回の振込前提**：設定の振込手数料を月次に1回分載せる（2026-09-19 決定） | SHOULD |

### 4.6 収集

| ID | 要件 | 優先度 |
|---|---|---|
| C-01 | 保存済みプロファイルでメルカリにアクセスする | MUST |
| C-02 | 初回は画面を表示し、手動ログインを受け付ける | MUST |
| C-03 | 売却済み一覧から取引を取得する | MUST |
| C-04 | 取得済みはスキップする（差分取得） | MUST |
| C-05 | セッション切れを検知し、画面に表示する | MUST |
| C-06 | 起動時、前回から間隔が空いていれば自動で取り込む | MUST |
| C-07 | **取得0件を異常（empty）として記録する** | MUST |
| C-08 | 実行履歴を残す | MUST |

**C-07の重要性**：画面構造は変わる。壊れたときに「0件＝正常」と誤認すると、
数ヶ月分のデータが静かに欠ける。

### 4.7 データ保全

| ID | 要件 | 優先度 |
|---|---|---|
| B-01 | DBファイルをバックアップできる | MUST |
| B-02 | 売上をCSVで書き出せる | MUST |
| B-03 | DBの保存フォルダを開ける | MUST |

ローカル1ファイルなので、退避手段は必須。

|---|---|

## 6. スコープ外

- メルカリへの書き込み操作（出品・価格変更・コメント）— **読み取りのみ**
- 複数端末での同期・共有
- 確定申告書の作成（集計までを担う）
- 在庫の自動発注・仕入判断の自動化

## 7. 留意事項

### 7.1 自動取得について

メルカリの利用規約は自動アクセスを制限している可能性がある。
本ツールは自分のアカウントの自分のデータを低頻度で読み取る用途に限定しているが、
**アカウント停止のリスクはゼロではない**。以下を守ること。

- 既定の間隔（1時間）を短くしない。1回に開くページは数ページまで、ページ間は 2〜6 秒空ける
- 書き込み操作は一切行わない
- 動作がおかしいと感じたら止める

より安全な代替として、売却通知メール・注文確認メールをGmail APIで読む方式がある。
メール文面はDOMより安定しており、規約上の懸念も少ない。Phase 2で併用を検討する。

### 7.2 税務・法務について

以下は専門家に確認すること。本ツールは判断を代替しない。

- 転売による所得の区分（雑所得か事業所得か）と申告要否
- 私物売却との切り分け方
- 継続的な転売に古物商許可が必要かどうか

### 7.3 「人の入力」と「自動取得の実額」がぶつかったとき（2026-09-20 決定）

- **送料**：取引画面から実額が取れたら、それが人の選んだ発送方法より優先して上書きされる（`shipping_source='actual'`）。実額のほうが帳簿として正しいため。上書きされたことは行の「自動取得」チップで分かる
- **紐付け**：人の決定（手動の紐付け・出品への引き当て）は自動より優先。自動で確定した紐付けは 1 クリックで外せる
- **販売を消しても、出品への引き当ては戻らない**（出品は sold のまま）。取り込み直しは新しい販売として入り、型番 FIFO か候補提示になる
- **タグ**：下流（在庫・販売）で派生タグは外せない。外すなら上流（仕入・在庫）で

## 8. フェーズ

### Phase 1（まず動かす）

スキーマ、収集、未処理一覧、紐付け、送料入力、仕入登録、月次集計、バックアップ。

**完成条件**：先月分の利益が、手計算と一致すること。

### Phase 2（型番で紐付ける）— 2026-09-19 決定

Phase 1 のレビューとメロジョイの商品コード調査を受けて決めた。**旧 Phase 2 の案（Gmail・発送方法の推定）は取り下げ、以下に置き換える。**

#### 2-A. 型番（商品コード）

メロジョイの商品名・バリアント名には `【Z078-2】` `【A035】` の形でコードが入っている。Shopify の SKU・product ID・variant ID は販売のたびに作り直されるため**主キーにしない**。安定しているのは商品名の中のコードだけ。

| ID | 要件 | 優先度 |
|---|---|---|
| K-01 | 正規表現 `/【([A-Z]\d{3}(?:-\d+)?)】/` でコードを抜く。バリアント名に【】があればそれが最小単位、なければ商品名側のコードが最小単位（`Z048-10` を「Z048 の 10 番」と解釈しない） | MUST |
| K-02 | `purchase_line` と `inventory_item` に `model_code`（最小単位）と `series_code`（先頭の `Z074`）を持つ。手動登録でも商品名から自動抽出し、手で直せる | MUST |
| K-03 | 素材（ムースクリーム／ねっとりヨーグルト／もちもちもち／クリーミークリーム）を名前から抜いて `material` に持つ。**在庫の表示名は素材を含める**（`Z056-1` / `Z056-2` は素材でしか区別できない） | MUST |
| K-04 | 数量は `2 * ボックス` `3*ボックス` から取る。A/B 系は箱のままが1点 | MUST |
| K-05 | 販売の取り込み・手入力時、タイトルと説明文から同じ形式でコードを抜く（複数可） | MUST |

**運用**：出品タイトルに型番【Z078-2】を必ず入れる。買い手も型番で検索するので不利にならない。

#### 2-B. 紐付け（ルール変更）

**「自動確定しない」を、型番の完全一致に限って緩める。**

| ID | 要件 | 優先度 |
|---|---|---|
| M-06 | 販売の型番が `model_code` と枝番まで完全一致 → その型番の未販売在庫を**古い順（先入先出）に1点**充てて自動確定。`sale_line.link_source = 'auto'`。画面に「自動」チップ、1クリックで解除 | MUST |
| M-07 | シリーズ一致のみ（`Z074` ↔ `Z074-3`）や型番なし → 自動確定せず候補の最上位に出す（従来どおり） | MUST |
| M-08 | タイトルに型番が複数（まとめ売り）→ それぞれの在庫を候補として同時に提示。確定は人間 | MUST |
| M-09 | 自動紐付けの原価は、充てた在庫の `landed_cost` をそのまま使う（同じ型番でも仕入ごとに送料按分が違う。先入先出で決める） | MUST |

#### 2-C. 在庫の分割・メモ

| ID | 要件 | 優先度 |
|---|---|---|
| I-06 | **ばらして売る**：在庫1点を N 点に分割できる。子の `landed_cost` は親を N 等分し端数は最後の子へ、合計は親と一致。親は `status = 'split'` で残す（過去の原価は動かない）。子は `parent_id` を持ち、型番は親を継ぐ（手で直せる） | MUST |
| I-07 | 仕入・販売・在庫にメモ欄を画面に出す（`note`） | MUST |
| I-08 | 自家消費・廃棄は Phase 1 のまま | — |

#### 2-D. 販売の実額

| ID | 要件 | 優先度 |
|---|---|---|
| S-08 | メルカリの**販売履歴ページ**（`/mypage/listings/sold`）の表から、商品・価格・**販売手数料・送料の実額**・購入完了日を取る（実DOM確認済み 2026-09-19。`src/main/__tests__/fixtures/mercari-sold.html`）。取れた販売は `shipping_source = 'actual'` として送料確定扱い（発送方法の選択が不要になる）。送料 ¥0 も実額。既知の販売も実額と本当の販売日で更新する | MUST |
| S-09 | キーワード（設定で複数指定可。`,` `、` 空白区切り。どれか1つでも含めば転売）を含まない取引は**私物として取り込む**。取り込まないのではない。設定が空なら型番の有無で判定 | MUST |
| S-10 | 販売の手入力は従来どおり。型番は商品名から自動抽出 | MUST |

#### 2-E. 仕入の取り込み

| ID | 要件 | 優先度 |
|---|---|---|
| P-06 | ~~mellojoy-watch の購入記録から下書きを作る~~ **取り下げ（2026-09-19、ユーザー指示：他ツールのフォルダを読まない）**。下書き（`purchase.status = 'draft'`）→確定の仕組みは P-07 用に残す | — |
| P-07 | メロジョイの注文履歴（Shopify 新カスタマーアカウント、アカウント別プロファイル `persist:mellojoy-<account>`）から注文番号・商品・バリアント・数量・価格・送料を取り、仕入に積む。「取り込む」と起動時の自動取り込みで、メルカリの後に有効な仕入先アカウントを順に読む（一覧1ページ＋詳細最大5件／回）。**明細の単価が整数で決まり、小計＋配送−割引＝合計が一致すれば確定（在庫生成）**。一致しなければ取れた値を入れた下書き（`draft`）にして人が確定する。キャンセル済みは飛ばす。`import_key = mellojoy:#注文番号` で二重取り込みを防ぐ。注文日は「確認日: 9月19日」（年なし）から推定。実 DOM は `__tests__/fixtures/mellojoy-orders.html` / `mellojoy-order.html`（2026-09-19 取得） | SHOULD |
| P-08 | TikTok Shop など他の仕入先は手動登録（型番は自動抽出） | MUST |
| P-09 | 仕入先アカウントに `kind`（mellojoy / tiktok / other）を持つ | MUST |

#### 2-F. 型番ランキング（ホーム）

| ID | 要件 | 優先度 |
|---|---|---|
| R-06 | バリアント（`model_code`）ごとに、仕入数・販売数・未販売数・平均売価・平均粗利・粗利合計をビュー `variant_summary` で集計し、ホームに上位を出す。並び替えは粗利合計／平均粗利／販売数 | MUST |

#### 2-G. 収集の振る舞い（Bot 対策）

自分のアカウントの自分のデータを、人間と同じ速度で読むだけ。**それ以上のことはしない**。

| ID | 要件 | 優先度 |
|---|---|---|
| C-09 | 収集ブラウザは普通の Chrome として見える状態にする：UA を通常の Chrome の文字列に、`Accept-Language: ja`、一般的なウィンドウサイズ、自動化を示すフラグ（`navigator.webdriver` 等）を出さない。ヘッドレスとしては起動しない（非表示の通常ウィンドウ） | MUST |
| C-10 | 1回の収集で開くページは数ページまで。ページ間は 2〜6 秒のランダム待ち。並列なし | MUST |
| C-11 | 既定 **1時間間隔**（起動時＋間隔経過時）。連打・リトライループなし | MUST |
| C-12 | 差分取得：既知の取引・注文は開かない。実額の取得は未入力の販売に限る | MUST |
| C-13 | **CAPTCHA・本人確認・「ロボットですか」が出たら即停止し、画面をユーザーに渡す**。自動突破はしない | MUST |


#### 2-I. 自動取得の判別とタグ（2026-09-19 追加）

| ID | 要件 | 優先度 |
|---|---|---|
| S-11 | 自動取得した販売と手入力の販売を画面で判別できる（`sale.source`）。紐付けの「自動」（型番一致）とは別の印にする | MUST |
| T-01 | タグを登録・改名・削除できる（設定タブ）。名前は一意 | MUST |
| T-02 | 販売と在庫にタグを複数付けられる。付け外しは1操作 | MUST |
| T-03 | 売上タブでタグで絞り込み、件数・売上・手数料・送料・原価・粗利の合計を見られる。合計は DB 側で集計する | MUST |
| T-04 | タグを消したら、付いていた販売・在庫からも外れる | MUST |

スキーマ：`tag(id, name UNIQUE, sort_order)`、`sale_tag(sale_id, tag_id)`、`inventory_tag(inventory_item_id, tag_id)`。

#### スキーマ変更（要点）

```
purchase        + status ('draft'|'confirmed')
purchase_line   + model_code, series_code, material
inventory_item  + model_code, series_code, material, parent_id, note   status に 'split'
sale            + shipping_source ('actual'|'master'|'manual'), model_codes（抽出したコードの JSON 配列）
sale_line       + link_source ('auto'|'manual')
shop_account    + kind
setting         collect_interval_h の既定を 1 に、mercari_keyword、mellojoy_watch_dir

```
