## Yahoo!フリマ：実物の DOM で分かったこと

**利用者に HTML をもらって確認した事実。推測ではない。** 次に触る人がここから始められるように残す。

### ページの役割分担

| ページ | URL | 取れるもの |
|---|---|---|
| 出品中 | `paypayfleamarket.yahoo.co.jp/my/item/selling` | 出品 id・**出品日時（unix秒）**・タイトル・価格・型番・いいね/閲覧数・総数 |
| 取引中・取引完了 | `…/my/item/sold` | **取引状態**（`tradstat`）・取引画面へのリンク。**日付は無い** |
| 売上金管理 | `salesmanagement.yahoo.co.jp/list` | **決済金額・販売手数料の実額**・取扱日・状態・商品 id。**CSV あり** |
| 受け取り明細 | `aucpay.yahoo.co.jp/detail-front/ReceiveDetailItem?_settle_id=…` | **出品先の判別**・分単位の日時・決済ID・購入者（マスク済み） |

### セレクタの当て方（クラス名に頼らない）

- フリマ側は **styled-components の自動生成クラス**（`sc-6e979adf-5` 等）でデプロイごとに変わる。**起点は `a[href^="/item/"]`、画像は `img[alt="商品画像"]`、価格は正規表現**
- 各行の `<a>` が持つ **`data-cl-params`** が最も安定：`rcconid`（商品 id）/ `opentime`（出品日時 unix秒）/ `tradstat`（取引状態）/ `viewcnt` / `wl`
- `tradstat` の値：出品中 `NONE`、売れて未発送 `WAIT_FOR_SELLER_SHIP`
- 売上金管理・受け取り明細は**古典的なサーバ描画**で `<dt>ラベル：</dt><dd>値</dd>`・`id="rcvdtl"` `id="itemnm"` `id="winyid"`。**ラベルの文字で引ける**＝壊れにくい
- **受け取り明細は文字コードが EUC-JP。** UTF-8 と決め打つと文字化けする
- 出品中の一覧は `__NEXT_DATA__` の `my.sellingItems` が**空**（クライアント描画）。ただし `my.todos` に **商品 id ごとの `createDate`（＝購入日時）** が入る。発送すると消えるので「未発送のあいだだけ」有効

### 商品 id

- Yahoo!フリマ … `[a-z]\d{8,}`（実例 `z693609190`。`b` `p` `t` `d` も観測）
- メルカリ … `m\d{9,}`
- **衝突しない。** ただし `[a-z]` はメルカリの `m…` も通すので、**先頭文字で出品先を当てる推測はしない**

### 型番はそのまま効く

出品タイトルに `【A035】``【Z072-14】``【Z088-01】` の形で入っており、既存の `code.ts` の `CODE_RE`（`/【([A-Z]\d{3}(?:-\d+)?)】/`）が**全部一致する**。**紐付けのロジックは1行も変えずに効く。**

### 手数料は率で計算できない（最重要）

実測：**6,400→320**（5%）／**5,899→294**（切り捨て）／**4,280→213**（5% なら 214 で**合わない**）／**5,200→0**（キャンペーン）。
**式が存在しない。** だから率は見込み専用で、**実額が取れたら必ず実額**。売上金管理の CSV から実額が取れる。

### まだ分かっていないこと

- **送料**。4 件とも `決済金額 − 手数料 = 受取額` で、送料が引かれていない（未発送のため）。**発送後に売上金管理をもう一度見る**
- **取引完了の見え方**と完了日（まだ完了した取引が無い）

### 個人情報

受け取り明細の購入者は `ran********` と**マスク済み**で、**住所・氏名は無い**。だからニックネームは安全に持てる（メルカリ側と同じ扱い）。ただし**取引画面**（`paypayfleamarket-sec…/trade/seller`）には発送用の氏名・住所があるはず。**DB にもテストにも入れない。**

## Yahoo!フリマ 第2段（自動取り込み）でやること

第1段では**あえて先送り**したもの。

| やること | なぜ先送りしたか |
|---|---|
| `sale.mercari_item_id` → `channel_item_id` の改名 | テーブル再構築を伴う。いま必要ない |
| `collector_run.source` の CHECK に `'yahoo'` | 同上（CHECK の変更は再構築）。共有型の `CollectorSource` も未対応 |
| 除外履歴は `deleted_sale` ではなく **`sale_exclusion`** | 名前を取り違えると旧列のまま残る（Codex の指摘） |
| `insertCollected` に `channel` 引数 | いまは列の DEFAULT `'mercari'` で正しいが、Yahoo を足すときは明示が必要 |
| `estimateSaleProfit`（紐付けパネルの粗利プレビュー）が**常にメルカリの率**で見積もる | 契約に `channel` が無い。Yahoo の販売に追加で紐付けるときのプレビューがずれる |
| 売上金管理の **CSV**（`POST /salesmanagelist_csv` に `.crumb` と `i=YYYYMM`） | DOM を読むより桁違いに安定。過去の月も取れる |

**次：Yahoo!フリマを出品先に足す（2段構え）**

| 段 | 何を | 必要なもの |
|---|---|---|
| 1 | **出品先の列＋出品先ごとの手数料＋手入力** | 不要（これだけで今日から Yahoo の売上を帳簿に入れられる） |
| 2 | Yahoo!フリマの自動取り込み | **販売履歴・取引詳細・出品中の HTML** |

第1段で触る構造（メルカリ前提は全 512 箇所あるが、効くのはここだけ）：

- `listing` の主キーが **`mercari_item_id TEXT PRIMARY KEY`**。`listing_line` の外部キー・トリガー・ビュー3つが参照 → テーブル再構築
- `sale.mercari_item_id TEXT UNIQUE`（`deleted_sale` の主キーにもなっている）
- `collector_run.source CHECK (source IN ('mercari','mellojoy'))` → `'yahoo'` を足すには再構築
- **手数料**：Yahoo!フリマは 2026-05-19 から**一律 5%**。しかも**おまかせ配送は「販売価格 − 送料」に対して 5%** ＝ 率だけでなく**計算の土台が違う**。`販売価格 × 率` で決め打っている箇所を全部洗う
- `sale.source` は `'collector'/'manual'`（取り込みか手入力か）なので、**出品先の列は新規に必要**
- 救い：**同じ在庫を同時に両社へ出品しない**（利用者の運用）ので、紐付けに新しい衝突ルールは要らない
